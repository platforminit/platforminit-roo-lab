## Findings

No blocking, high, medium, or low severity security/privacy findings were identified in the changed behavior.

### Source-selection and injection boundary — CLEAR

The registration and validator accept only `rehearsal|stable`, reject contradictory promotion/mode combinations, derive the expected repository from the selected mode, and require an exact repository match. The repository URL is restricted to HTTPS syntax, rejects embedded userinfo, and is then compared against the two exact PlatformInit repository URLs. Rehearsal validation requires a revision and rejects floating revisions unless the explicit branch-rehearsal opt-in is present. Stable mode rejects abbreviated revisions and requires the stable-source promotion flag. The target revision character allowlist excludes shell, YAML, and `sed` metacharacters relevant to its use.

The workflow exposes `gitops_source_mode` as a choice input and passes the selected value through a quoted environment variable. Stable mode additionally fails before remote execution when `target_revision` is absent. The diagnostics workflow retains the rehearsal default and does not introduce a stable-source switch. Harness paths and file reads are quoted; harness content is compared as data rather than evaluated.

### Live-source and AppProject trust boundary — CLEAR

The post-registration assertion checks repository, revision, project, and single-source state. The validator explicitly rejects a rehearsal Application syncing the stable repository, foreign repository entries, wildcard source entries, extra `spec.sources`, wrong project, and missing contract source. The AppProject source list contains only the two exact intended PlatformInit repositories and no wildcard. This closes the implicit-source-switching and foreign-repository widening paths described by the acceptance criteria.

The documented unresolved casing compatibility risk (legacy `PlatformInit` URL spelling) is fail-closed repository registration behavior, not an unintended source acceptance path. Manual rehearsal registration without `TARGET_REVISION` also fails closed by design. Stable promotion requires the explicit source flag and revision; partial promotion inputs do not silently select a source. Empty `spec.sources` output is treated as the expected single-source representation, while a non-empty non-`[]` value is rejected.

### Secret handling and evidence leakage — CLEAR for this change

The changed source-contract values are repository URLs, mode, and revision; no secret values are added to manifests, command arguments, logs, GitHub outputs, or uploaded reports. Credential-in-URL input is rejected before rendering or cluster access. Existing CH05 handling still transfers operational secrets through the pre-existing temporary environment-file path; that path was inspected as a directly required trust boundary and no new secret exposure was introduced by this patch. The review did not print or copy any secret value.

### Privilege, supply chain, and forbidden-action boundary — CLEAR

The patch does not add permissions, third-party actions, installers, sudo grants, destructive cloud/Kubernetes operations, Authentik/OIDC/header changes, DNS/Cloudflare operations, or GitHub secret/environment mutation. Existing workflow permissions remain `contents: read` and `actions: read`. The narrowed exact AppProject repository allowlist reduces source supply-chain scope; resource wildcards and existing CH05 runtime ownership are unchanged and outside this source-contract change.
